Student Data Analyser: how to use it

Start here

This tool answers questions about student enrolment data. Instead of writing a query in a language, you build the question out of parts. Each part is a node on the canvas. You wire nodes together, and the data flows along the wires from left to right.

Every query has the same three parts:

  1. A Source, where the rows come from. Every query starts with one, and you have to give each Source its data files before it can run. See Loading the data.
  2. The middle: any number of nodes that narrow, reorder, summarise or combine those rows. You add them from the Reshape and Processing menus. This part can be empty.
  3. An Output, where the answer appears in the panel on the right.

Nothing is calculated until you press Run Query. Until then the canvas is just a description of a question, so you can build and rearrange it freely without waiting for anything.

The quickest possible start: click Source, load headers.txt and then a mcs-students- year file into it, click Output, drag the Output near the Source until a wire appears, and press Run Query.

Loading the data

The tool ships with no data at all. You give every Source its own files, and until it has them it will not run. A Source with nothing loaded shows a dashed ring with an amber dot on it, and pressing Run Query tells you which one to fix.

There are two files, and they go in this order:

  1. headers.txt, the column names and the numbering under them. This has to come first. A year file is a grid of tab-separated fields with no names on it, so nothing can be read out of one until the tool knows what each position holds.
  2. mcs-students-2022 and friends: one file per year, named for the year, with no extension. Choose as many as you like, in as many goes as you like. The Source then answers about all of them together, or about one year at a time through its Population setting.

One column file, many year files. A Source holds a single headers.txt, because one column list describes the shape of every year file. The years are a collection it builds up instead. Add puts more in beside what is already loaded rather than replacing them, so 2022 and 2023 today plus 2024 when it arrives is three trips to the file picker and nothing to re-choose.

Each loaded year is listed under step 2 with its own student count and its own x to take just that one back off. Removing the last of them leaves headers.txt in place, so you can pick different years straight away. Use Unload everything when you want to clear both.

Choosing a year the Source already holds replaces that year, which is what you want when a corrected export arrives. The panel says Replaced 2022 rather than making the swap silently, since holding both copies would count that cohort twice.

If any file in one selection is refused, none of that selection loads and whatever the Source already held is left exactly as it was. A half-loaded Source would be answering about a cohort nobody asked for.

The file names are not a convention you can bend. A file is only read if it is named exactly headers.txt, or exactly mcs-students- followed by a four-digit year. Anything else is refused on its name before a single byte is read, and the panel tells you what it was expecting.

Renaming a file does not change what is inside it, and the tool checks. A file called mcs-students-2023 whose rows are 2022 enrolments is refused, and so is a year file whose rows do not carry exactly as many fields as headers.txt declares. Both refusals name the line that failed, so you can find a bad export rather than guess at it.

Each Source owns its files. Two Sources can hold two different sets of years and be compared against each other: load 2022 into one and 2023 into the other, then wire both into a Compare. If you want one Source to span several years, just load several year files into it.

Eight columns are read: the ID, gender, the first degree, the first major, the year, the course, the grade and the points. Names, usernames, email addresses and ethnicity are in the file, and the tool deliberately does not keep them. Data that is never loaded cannot leak out of an export or a screenshot.

One more column is worked out rather than read. The first digit of a course code says what level it is taught at, so CGRA151 is 100-level and SWEN421 is 400-level. Every enrolment therefore gets a Level alongside its subject. The archive is not a single honours year: 2022 alone holds 697 enrolments at 100-level against 454 at 400-level, and averaging those together without being able to see the difference gives you an answer that is wrong without looking wrong.

Level is a number, so you can measure it. Took level on a Filter keeps students who took at least one course at a given level, and since the comparisons come with it, at 300-level or above becomes the progression question. Put a Project in front of an Aggregate to ask for the highest level a student reached, or the average level across a cohort.

The toolbar

Everything you can do to a query lives along the top, grouped by purpose: build it on the left, manage the file in the middle, change your view on the right.

Making the toolbar bigger

The edge along the bottom of the bar can be dragged downwards, and the controls grow with it, so a bar you have pulled down is a bar with bigger buttons rather than one with the same buttons floating in a gap. Drag it back up, or double-click it, to return to the starting size.

It stops when the controls would run off the edge of the window or leave too little canvas to build in, so there is no way to pull it far enough to lose a button. On a narrower window the groups wrap onto a second row rather than being pushed out of sight. Like the panel width, the size you settle on is remembered and is yours alone: it is not part of a saved query.

Anatomy of a node

Every node has the same two parts: a coloured shape you drag around, and a settings panel underneath it. The shape tells you what kind of node it is, and the panel tells you what this particular one does.

Connecting nodes

There are no wires to draw by hand. Drag one node near another and a wire appears between them. Drag it away again and the wire goes. The direction is worked out from what the two nodes are, so a Filter dropped beside a Source is always fed by it, never the other way round.

To branch, wire several nodes to the same source. One table can feed any number of nodes downstream, and that is how you ask two questions of one population and then bring the answers back together with Compare.

Node reference

Two menus hold the twelve nodes that sit between a Source and an Output, split by what each one does to the shape of the table. A node's colour on the canvas is its group, so you can read an unfamiliar graph at a glance and see where it narrows, where it multiplies, where it collapses, and where branches meet.

Reshape is the menu you will reach for most, and it is the one group whose nodes all leave the meaning of the table intact: a row is still whatever it was before. Processing holds the three groups that change that. Expand makes a row mean something new, Summarise replaces many rows with one, and Branches pulls several tables into one.

Source

Where a query begins. It reads the rows in the data file and hands them on, one row per student, with that student's courses carried inside the row. Every query needs at least one, and a query with none has nothing to compute. Several Sources in one graph is perfectly normal, and it is how you reach across years.

Filter

Keeps the rows that match a condition and discards the rest. Add more than one condition to narrow things further, and a row then has to satisfy all of them. The fields on offer come from whatever is arriving, and the comparison changes to suit the column: a number gets at least and at most, while a category gets is and is not.

The comparison dropdown holds six comparisons under Compare, and one more under Range. Choosing in range opens an amber band under the condition with a bound at each end. Both ends count as inside, so a mark range of 70 to 80 keeps a mark of exactly 80. Entering the bounds the other way round means the same band, and the query log prints the one that was actually applied.

Ranges are offered wherever the ordering is a real one: on any number, on Year, and on Grade, whose letters carry a declared ranking from A+ down to D. That makes “grade between A+ and B” a band of grades rather than a comparison of spellings. They are not offered on Gender or Specialisation, where the only ordering would be the order somebody typed the list in.

Reshape (violet)

The same data, narrowed or reordered. Nothing is summarised.

Sort
Orders rows by a column, ascending or descending. Add further keys to break ties: the first key decides, the second settles what the first left equal.
Reverse
Turns the row order upside down. Same rows, same columns, same count, with the last row becoming the first. Its real use is in front of Take. Take keeps the first N rows, so Sort, Reverse, Take is how you ask for the last N. It needs no column, which is what lets it work on a table whose order did not come from a Sort at all: the order rows arrived in from a Combine, or the order branches were wired into a Compare.
Take
Keeps the first N rows and drops the rest. On its own that is arbitrary, so it is nearly always used straight after a Sort. Together they mean top N, or bottom N with a Reverse between them.
Unique
Two modes. With no column named it removes duplicate rows by comparing whole rows. Name a column and it gives you that column's distinct values instead, one per row, which is how you get a list of the courses or the years present in a table.
Select
Keeps the columns you tick and drops the rest. The rows are untouched, so you get the same rows in the same order with the same count. This narrows a table without summarising it. Put one in front of an Output to show three columns instead of seven, or in front of an Aggregate to make it plain which column is being measured. Columns stay in the order they arrive, and you have to keep at least one.

Expand (lime)

The one node that changes what a row means, which is why it has a group to itself.

Project
Turns each row into one row per course taken, so a student with eight courses becomes eight rows. From here on a row is an enrolment, not a student, and a Count after a Project counts course registrations rather than people. The node says as much on its panel, and the query log prints the row counts before and after, because this is the one step that can make a later number look eight times too big.

It is also how a mark or a grade in a particular course becomes something you can filter, sort or average. Without it the tool can tell you whether a student took SWEN421 but never what they got for it, because the marks sit nested inside the row rather than in a column of their own. Wire it after a Source, filter on Course, and from that point Mark and Grade are ordinary columns.

To get back to one row per student afterwards, use Unique on Student.

Summarise (teal)

Rows collapse to a summary, and the columns are rewritten.

Aggregate
Reduces the whole table to a single value: a count, sum, average, median, minimum or maximum of one column.
Aggregate Columns
One row out, with the chosen calculation applied to every numeric column at once. Use it for a profile of a group rather than a single figure.
Aggregate Rows
The mirror of Aggregate Columns, and the one that runs across the page instead of down it: one value for every row, and a single column out. The row count does not change. It replaces the whole row rather than adding to it, because totalling a row that still carries an ID is not a meaningful thing to have done. Put a Select in front to narrow the row down to the figures you actually mean to combine.

Branches (rose)

Several tables in, one out. These are the only nodes that take more than one wire.

Select For
A breakdown: one row per group, with the measures you pick alongside. Name the column to split on, such as For each Year or For each Degree, and it runs that split once per value. That turns “how many in each year, and their average mark” into one node instead of one branch per year.
It groups by the same things a Filter can test, including the ones that are not really columns. Took course and Took subject reach inside a student's course list, so you can break a cohort down by course without a Project first. A row stays a student, and a count stays a count of students.
It has a second input called Labels, and leaving it empty is the common case: the groups are then whatever values happen to be in the data. Wire a one-column table in and those values become the groups instead, which buys you two things the data alone cannot give. First, a group that nothing matches still gets a row, with a count of zero, and a course nobody took this year is usually exactly the row you are looking for. Second, the groups can come from a different branch entirely, such as the courses that ran in 2022 measured against the enrolments of 2024.
It does not reorder anything. Put a Sort after it, and then a Take after that, if you want the largest few.
Combine
Four modes, in two kinds. Merge adds vertically, stacking branches into one longer table, so their columns have to match. Duplicates are kept unless you ask for them to be dropped. Intersect and Difference narrow that stack to the rows present in every branch, or present in the base alone, which is how you ask who left between two years.
Join adds horizontally instead. It matches rows on a column you name and puts the other branches' columns onto the end of each base row, so one student's 2022 and 2023 figures sit side by side on a single row. The result has the base's rows and never more. A base row with no match is dropped unless you tick Keep base rows with no match, which leaves the missing cells blank instead. Where two branches carry the same column name, the incoming one is renamed after the node it came from rather than overwriting what is already there.
Compare
Puts branches beside each other instead: one row per branch, with a column per measure. Use it to hold two populations up against one another rather than to pool them. It suits branches that are not a split of anything, which is the one case Select For cannot cover.
Where the branches are a split of one column, such as a branch per year or a branch per degree, Select For says the same thing in a single node instead of one wire per group, and it can say it for values that are not in the data yet. Compare is kept for the other case, and for queries already built on it.

Output

Where an answer appears. Each Output becomes a block in the results panel, and a graph may have several, so one run can answer several questions at once. Its setting chooses between showing the rows themselves and showing how many of them there are. It only displays what arrives, so for an average or any other figure, wire an Aggregate in front of it.

When it is showing the rows, it also offers a tick box per column, so you can look at three columns of a wide table without wiring anything up. This changes the view and never the answer: no rows are lost, and Copy and Save write exactly the columns shown. A Select upstream does the same job to the data itself, and the two work together, with Select narrowing what arrives and this narrowing what you see of it.

Reading results

Pressing Run Query fills the panel on the right, one block per Output node, in the order the Outputs were added.

Making the panel wider

The panel starts narrow so that the canvas has room. When a table has more columns than fit, there are two ways to widen it, and the canvas gives up the space rather than being covered.

  • Wide, at the top of the panel, opens it far enough to read a full row at once. The button then reads Thin, and pressing it puts the panel back. W does the same.
  • The edge between the canvas and the panel can be dragged to any width in between. Double-click it to return to the starting width.

Whichever width you settle on is remembered the next time you open the tool. It is a setting of your own rather than part of a query: saved .json files carry the graph only, so opening someone else's query leaves your layout alone.

Check a query rather than trusting it. Every node shows its own row count after a run, and hovering a wire shows the table passing along it. Between them you can follow the data step by step and find the point where a result stopped being what you expected.

Saving a query

Save writes the whole graph to a .json file, meaning every node, its settings and every wire, and it asks you to name the file first. The .json ending is fixed, so a saved query is always one the tool can open again. Save a second time and it offers the name you used before, so revising a query does not scatter near-identical files around.

Load opens one back onto the canvas, replacing whatever is there. Only .json files are accepted.

What a file holds is the question, not the answer. Opening a saved query restores the graph, and pressing Run Query evaluates it against the data as it stands at that moment, so the same query re-run next year gives you next year's answer.

The data is never saved with it. A query file records the names of the files each Source was given and nothing out of them: no student, no grade, not even a course code. That is deliberate. Queries get emailed around, and student records should not travel with them.

So loading a query gives you the graph back with every Source empty, and each Source then names the files it was built against. Choose them again and the query answers exactly as it did before. A query saved last year and loaded against this year's files is the same question asked of new data, which is the whole point of keeping one.
