Student Data Analyser: how to use it

Guided walkthrough

A short walk around a query that is already built, so you can see what the parts are before you make one yourself. It puts a small practice query on the canvas and then talks you through it, one part at a time.

Nothing is asked of you and nothing is loaded from your own files. You can leave at any point with Escape, and the practice query stays on the canvas afterwards so you can take it apart, change it, or run it against real data.

It replaces what is on the canvas. If you have a query you want to keep, save it first. The button will ask you once before it does anything.

Start here

This tool answers questions about student enrolment data. Instead of writing a query in a language, you build the question out of parts. Each part is a node on the canvas. You wire nodes together, and the data flows along the wires from left to right.

Every query has the same three parts:

  1. A Source, where the rows come from. Every query starts with one, and you have to give each Source its data files before it can run. See Loading the data.
  2. The middle: any number of nodes that narrow, reorder, summarise, combine or count up those rows. You add them from the Reshape, Processing and Distribution menus. This part can be empty.
  3. An Output, where the answer appears in the panel on the right.

Nothing is calculated until you press Run Query. Until then the canvas is just a description of a question, so you can build and rearrange it freely without waiting for anything.

The quickest possible start: click Source, load headers.txt and then a mcs-students- year file into it, click Output, drag the Output near the Source until a wire appears, and press Run Query.

Loading the data

The tool ships with no data at all. You give every Source its own files, and until it has them it will not run. A Source with nothing loaded shows a dashed ring with an amber dot on it, and pressing Run Query tells you which one to fix.

There are two files, and they go in this order:

  1. headers.txt, the column names and the numbering under them. This has to come first. A year file is a grid of tab-separated fields with no names on it, so nothing can be read out of one until the tool knows what each position holds.
  2. mcs-students-2022 and friends: one file per year, named for the year, with no extension. Choose as many as you like, in as many goes as you like. The Source then answers about all of them together, or about one year at a time through its Population setting.

One column file, many year files. A Source holds a single headers.txt, because one column list describes the shape of every year file. The years are a collection it builds up instead. Add puts more in beside what is already loaded rather than replacing them, so 2022 and 2023 today plus 2024 when it arrives is three trips to the file picker and nothing to re-choose.

Each loaded year is listed under step 2 with its own student count and its own x to take just that one back off. Removing the last of them leaves headers.txt in place, so you can pick different years straight away. Use Unload everything when you want to clear both.

Choosing a year the Source already holds replaces that year, which is what you want when a corrected export arrives. The panel says Replaced 2022 rather than making the swap silently, since holding both copies would count that cohort twice.

If any file in one selection is refused, none of that selection loads and whatever the Source already held is left exactly as it was. A half-loaded Source would be answering about a cohort nobody asked for.

The file names are not a convention you can bend. A file is only read if it is named exactly headers.txt, or exactly mcs-students- followed by a four-digit year. Anything else is refused on its name before a single byte is read, and the panel tells you what it was expecting.

Renaming a file does not change what is inside it, and the tool checks. A file called mcs-students-2023 whose rows are 2022 enrolments is refused, and so is a year file whose rows do not carry exactly as many fields as headers.txt declares. Both refusals name the line that failed, so you can find a bad export rather than guess at it.

Each Source owns its files. Two Sources can hold two different sets of years and be compared against each other: load 2022 into one and 2023 into the other, then wire both into a Compare. If you want one Source to span several years, just load several year files into it.

Eight columns are read: the ID, gender, the first degree, the first major, the year, the course, the grade and the points. Names, usernames, email addresses and ethnicity are in the file, and the tool deliberately does not keep them. Data that is never loaded cannot leak out of an export or a screenshot.

One more column is worked out rather than read. The first digit of a course code says what level it is taught at, so CGRA151 is 100-level and SWEN421 is 400-level. Every enrolment therefore gets a Level alongside its subject. The archive is not a single honours year: 2022 alone holds 697 enrolments at 100-level against 454 at 400-level, and averaging those together without being able to see the difference gives you an answer that is wrong without looking wrong.

Level is a number, so you can measure it. Took level on a Filter keeps students who took at least one course at a given level, and since the comparisons come with it, at 300-level or above becomes the progression question. Put a Project in front of an Aggregate to ask for the highest level a student reached, or the average level across a cohort.

The four grade columns, and which is which

The archive records one letter per enrolment and nothing else. Everything else about grades is worked out from that, which is why there are four columns and not one. Two of them describe a single course and two describe a whole student.

Grade
one course		 The letter actually awarded, from A+ down to D, E and K. Only on a row that is an enrolment, so you need a Project to reach it.
Grade points
one course		 That same letter as a number, A+ being 9 and D, E and K all 0. The form you can average; the letters themselves cannot be added up.
GPA
one student, one year		 The average of those points across everything the student was graded on that year, weighted by the points each course is worth, so a 30-point project counts twice a 15-point course. An ungraded enrolment is left out rather than counted as a zero.
Overall grade
one student, one year		 The GPA rounded to the nearest letter. A GPA of 6.4 shows as B+, so this is a summary of the year and not a grade anyone was given.

Each pair is one fact in two forms, and both forms earn their place: the numbers are what an Aggregate can measure, and the letters are what a question is usually asked in. Neither is a second copy of the data, because the tool knows the ranking of the letters, so grade between A+ and B is a band on either form rather than a comparison of spellings.

Grade and Overall grade are different questions. Before a Project a row is a student and the grade column is their standing for the year; after one a row is an enrolment and the grade column is what they got for that course. The two are named apart so a header tells you which you are looking at, and a Project replaces the first with the second rather than carrying both.

The toolbar

Everything you can do to a query lives along the top, grouped by purpose: build it on the left, manage the file in the middle, run it on the right. Changing your view is not in the bar at all, because it is not something you do to a query: those controls sit on the canvas, in its bottom left corner.

Zoom and Fit are on the canvas

The view controls are not in the bar. They sit in a small panel in the bottom left of the canvas: zoom out, the current zoom, zoom in, and Fit. Clicking the percentage returns you to 100%, and Fit brings every node back on screen.

They are there because that is what they act on. Everything in the bar is about the query; these are about nothing but your view of it, and none of them changes the answer. The bottom left is also the one corner nothing else uses, so they never cover the selection bar that appears along the bottom when nodes are picked. +, −, F and scrolling do the same jobs from the keyboard.

Making the toolbar bigger

The edge along the bottom of the bar can be dragged downwards, and the controls grow with it, so a bar you have pulled down is a bar with bigger buttons rather than one with the same buttons floating in a gap. Drag it back up, or double-click it, to return to the starting size.

It stops when the controls would run off the edge of the window or leave too little canvas to build in, so there is no way to pull it far enough to lose a button. On a narrower window the groups wrap onto a second row rather than being pushed out of sight. Like the panel width, the size you settle on is remembered and is yours alone: it is not part of a saved query.

Anatomy of a node

Every node has the same two parts: a coloured shape you drag around, and a settings panel underneath it. The shape tells you what kind of node it is, and the panel tells you what this particular one does.

Switching a node off. Select a node and press M, or use Switch off in the bar at the bottom of the canvas. A node that is off goes grey, its border turns dashed, and it says (Off) under its name. It stays wired and keeps every setting; it simply stops doing its job and passes its data straight through, so the rest of the query runs exactly as if that one step were not there.

This is the quick way to ask what a query looks like without one of its steps. Deleting the node would answer the same question, but it throws away the settings and leaves two loose ends to wire back together. Pressing M again puts it back. To switch off a whole arm of a query at once, double-click any node in it to select the branch, then press M.

A Source cannot be switched off, because it has nothing arriving to pass through. An Output can, and when it is, its block leaves the results panel.

Connecting nodes

There are no wires to draw by hand. Drag one node near another and a wire appears between them. To take one out, hover over the wire and click the x that appears halfway along it: dragging the two nodes apart again moves them, and leaves the wire where it was. The direction is worked out from what the two nodes are, so a Filter dropped beside a Source is always fed by it, never the other way round.

To branch, wire several nodes to the same source. One table can feed any number of nodes downstream, and that is how you ask two questions of one population and then bring the answers back together with Compare.

Node reference

Three menus hold the thirteen nodes that sit between a Source and an Output, split by what each one does to the shape of the table. A node's colour on the canvas is its group, so you can read an unfamiliar graph at a glance and see where it narrows, where it multiplies, where it collapses, and where branches meet.

Reshape is the menu you will reach for most, and it is the one group whose nodes all leave the meaning of the table intact: a row is still whatever it was before. Processing holds the three groups that change that. Expand makes a row mean something new, Summarise replaces many rows with one, and Branches pulls several tables into one. Distribution holds the two nodes that answer a different kind of question altogether: not what the rows are, but how they are spread out.

Source

Where a query begins. It reads the rows in a data file and hands them on. Every query needs at least one, and a query with none has nothing to compute. Several Sources in one graph is perfectly normal, and it is how you reach across years.

A data file carries no column names inside it, so a Source is given two files: the column file that names the columns, and then the data itself. Name the column file headers.txt, or headers- then the data file's name and .txt, so that a folder can hold several data files and the columns for each of them side by side: headers-gpa-bands.txt describes gpa-bands.txt.

The columns decide how the file is read, and there is nothing to choose. A column file naming the archive's columns (ID, Year, Crse, Grade and the rest) means student records, and the rows are folded into students with their courses nested inside them. Any other column file means an ordinary table, and the rows come through as they are: one row per line, no students and no years. That is how a list of labels or a file of named bands gets in, which is what Select For's Labels port takes. The panel says which of the two it is reading before you load anything into it.

A table file is read as it finds it. Tabs, commas or spaces, whichever separates the first row into as many fields as the column file names; a column whose every value reads as a number becomes a number column, so it can be measured, sorted or used as a band edge; and a row with the wrong number of fields is padded or trimmed to fit and counted in the notice rather than refusing the file.

Rows and Population below are about students, so a Source reading an ordinary table shows neither. Rows chooses what a row means on the way out, and it is the setting that changes every count downstream. One row per student is the default: a row is one student in one year, with that student's courses carried nested inside the row, so a student who appears in two years is two rows and each cohort is separately countable. One row per enrolment unfolds those courses into rows of their own, so one student becomes one row per course they took and a Count counts course registrations rather than people.

Because that difference is easy to read past, a Source set to enrolments says one row per enrolment on the node itself, its panel states the multiplication in this Source's own numbers, and the query log prints the row counts either side of the change. It is the same unfold a Project node performs, and the same rename comes with it: ID arrives as Student, because after the unfold it no longer identifies a row. Use the setting when every branch of the query wants enrolments, and a Project when only one branch does.

Filter

Keeps the rows that match a condition and discards the rest. Add more than one condition to narrow things further, and a row then has to satisfy all of them. The fields on offer come from whatever is arriving, and the comparison changes to suit the column: a number gets at least and at most, while a category gets is and is not.

The comparison dropdown holds six comparisons under Compare, and one more under Range. Choosing in range opens an amber band under the condition with a bound at each end. Both ends count as inside, so a mark range of 70 to 80 keeps a mark of exactly 80. Entering the bounds the other way round means the same band, and the query log prints the one that was actually applied.

Took course and Took subject also offer matches, which takes a pattern rather than a value. * stands for any run of characters and ? for exactly one, so SWEN* is every SWEN course, *4?? is every 400-level course whatever the subject, and SWEN3?? is 300-level SWEN. The pattern is the whole code rather than part of it, so COMP matches nothing, and capitals do not matter.

One pattern over Took course reaches what Took subject and Took level reach, which is the point of it: fewer conditions for the same question. The two fields stay, because picking a subject from a list is easier than remembering a pattern. Everything other than * and ? is matched literally, so there is no pattern that can be written wrongly.

Ranges are offered wherever the ordering is a real one: on any number, on Year, and on either grade column, whose letters carry a declared ranking from A+ down to D. That makes “grade between A+ and B” a band of grades rather than a comparison of spellings. They are not offered on Gender or Specialisation, where the only ordering would be the order somebody typed the list in.

Expand (lime)

The one node that changes what a row means, which is why it has a group to itself.

Project
Turns each row into one row per course taken, so a student with eight courses becomes eight rows. From here on a row is an enrolment, not a student, and a Count after a Project counts course registrations rather than people. The node says as much on its panel, and the query log prints the row counts before and after, because this is the one step that can make a later number look eight times too big.

It is also how a mark or a grade in a particular course becomes something you can filter, sort or average. Without it the tool can tell you whether a student took SWEN421 but never what they got for it, because the marks sit nested inside the row rather than in a column of their own. Wire it after a Source, filter on Course, and from that point Grade and Grade points are ordinary columns.

To get back to one row per student afterwards, use Unique on Student.

A Source can do this unfold itself, with its Rows setting. The result is identical; what differs is reach. The setting changes every branch that leaves that Source, which is what you want when the whole query is about courses. This node changes one branch, and shows on the canvas where the change happened, which is what you want when another branch still needs to count people.

Summarise (teal)

Rows collapse to a summary, and the columns are rewritten.

Aggregate
Reduces the whole table to a single row. Add a measure for each figure you want on it: a count, sum, average, median, minimum or maximum, each of a column you choose. One measure gives one value, which is the commonest use; a minimum and a maximum together give a range, and there is no need to build two branches and join them back up for it.

Comparing two columns. The Measure list has a second section, Between two columns, holding Difference, Ratio and Percent of. These read two columns you name rather than running along the whole row, and the order matters, so picking one gives you an Of box and a second box beside it. They are how you ask for a rate or a change: join the branch that counts everyone to the branch that counts the ones you are interested in, then take one as a percent of the other. The result is an ordinary column, so Sort will rank by it and Filter will cut it down, which is the point of having it rather than reading the two numbers off the row yourself.

A row with a blank on either side, or a zero to divide by, comes out blank rather than guessed at, and the query log says how many rows that happened to. A column that is neither of the two you named is carried through untouched.

Branches (rose)

Several tables in, one out. These are the nodes that take many wires on a single port.

Combine
Four modes, in two kinds. Merge adds vertically, stacking branches into one longer table, so their columns have to match. Duplicates are kept unless you ask for them to be dropped. Intersect and Difference narrow that stack to the rows present in every branch, or present in the base alone, which is how you ask who left between two years.
Join adds horizontally instead. It matches rows on a column you name and puts the other branches' columns onto the end of each base row, so one student's 2022 and 2023 figures sit side by side on a single row. The result has the base's rows and never more. A base row with no match is dropped unless you tick Keep base rows with no match, which leaves the missing cells blank instead. Where two branches carry the same column name, the incoming one is renamed after the node it came from rather than overwriting what is already there.
Under Name the inputs you can say what each branch is called, and that name heads the columns it brings instead of the node's own. A branch bringing one column is headed by the name alone, so three branches named 2022, 2023 and 2024 give you a table with those three headings. A branch bringing several has the name added to each of them. Leave a box empty and that branch keeps its automatic name.
Example
In

Ana6.2
→
Out
StudentGPA 2022GPA 2023
Jo7.87.1

Settings: Mode Join, Base the 2022 branch, Match rows on Student, and the two branches named GPA 2022 and GPA 2023. Without those names the second column would have read GPA · Select For #5, after the node rather than the year. Merge would have stacked these into four rows instead.

Compare
Puts branches beside each other instead: one row per branch, with a column per measure. Use it to hold two populations up against one another rather than to pool them. It suits branches that are not a split of anything, which is the one case Select For cannot cover.
Where the branches are a split of one column, such as a branch per year or a branch per degree, Select For says the same thing in a single node instead of one wire per group, and it can say it for values that are not in the data yet. Compare is kept for the other case, and for queries already built on it.

Distribution (indigo)

How the rows are spread, rather than what they are. One row per group, with the measures you ask for beside it: Select For splits on the values of a column, Histogram on ranges of a number.

Select For
A breakdown: one row per group, with the measures you pick alongside. Name the column to split on, such as For each Year or For each Degree, and it runs that split once per value. That turns “how many in each year, and their average mark” into one node instead of one branch per year.
It groups by the same things a Filter can test, including the ones that are not really columns. Took course and Took subject reach inside a student's course list, so you can break a cohort down by course without a Project first. A row stays a student, and a count stays a count of students.
It has a second input called Labels, and leaving it empty is the common case: the groups are then whatever values happen to be in the data. Wire a one-column table in and those values become the groups instead, which buys you two things the data alone cannot give. First, a group that nothing matches still gets a row, with a count of zero, and a course nobody took this year is usually exactly the row you are looking for. Second, the groups can come from a different branch entirely, such as the courses that ran in 2022 measured against the enrolments of 2024.
The one-column table comes from Unique, which is what that node's named column mode is for: a Source, then Unique on Course, gives you every course present in that branch, one per row. Narrow or extend it with the ordinary nodes before it reaches the port, and a Sort and a Take in front of Labels are how you say "the ten biggest". A Source cannot supply one: it reads the archive files and always produces the archive's columns.
Wire in a table of three columns instead and the groups become named bands rather than values. The columns are read in order: the first names the band, the second is its lowest value and the third its highest, so a file reading Fail 0 4 / Pass 4 6 / Merit 6 8 / Excellent 8 9 is a grading scheme, and the same four rows are the same scheme next year. That is the difference between this and a Histogram, whose band widths come from the data it is given and so differ between one year and the next. Here you say what the bands are, and Put in bands names the number they apply to.
A value sitting on the edge between two bands goes in the higher one, so bands that meet never count it twice and the bands still add up to the rows. The very top of the last band is included, which is what those four rows mean by 8 9 covering an A+. A row whose value falls in no band at all is left out and counted in the query log, as is a row with no value to compare, so a breakdown that quietly lost a third of its rows says so.
The node works out which of the two readings you meant from the shape of the table, and says which one it chose under Read the Labels branch as. Set it there if it guesses wrong, which it can: a Histogram with two measures has three columns and the last two are numbers, and it is not a set of bands.
It does not reorder anything. Put a Sort after it, and then a Take after that, if you want the largest few.

202227.00
202315.10

Settings: For each Year, Measure Count and Average of GPA. Labels is empty, so the groups are the years found in the data.

Histogram
Counts the rows into bands of a number you choose: how many students in each GPA band, how many enrolments at each mark. Pick the column and the width of a band, and you get one row per band with a count beside it, plus any other measure you add.
For anything with only a few values, you do not need this node at all. Select For grouped by Overall grade is already a grade distribution, in the declared A+ to D order. Histogram is for the columns where grouping by value would give you one row per student, which is every genuinely numeric one.
Bands start at a multiple of the width, not at the smallest value in your data. That is what makes two years binned the same way comparable: bands of 1 always run 4 to 5 and 5 to 6, whoever is looking and whatever year they loaded.
A value on a boundary belongs to the band above it, except at the very top, where the last band is closed so the largest value has somewhere to go. This is the one rule you cannot check by looking at the result, and it is what makes the counts add up to the rows you started with rather than double-counting every boundary.
A band nothing falls in is still a row, with a count of zero, because a gap in the middle of a distribution is usually the thing worth seeing. Rows with no value at all, like a withdrawn enrolment with no mark, are in no band and are reported separately in the query log: a missing mark is not a mark of zero.
It does not reorder. The bands come out in order, and the column knows that order, so a Sort after it sorts by band properly rather than alphabetically.

Settings: Distribution of GPA, In bands of 1. A band nothing falls in still gets a row, with a count of zero.

Output

Where an answer appears. Each Output becomes a block in the results panel, and a graph may have several, so one run can answer several questions at once. Its setting chooses between showing the rows themselves and showing how many of them there are. It only displays what arrives, so for an average or any other figure, wire an Aggregate in front of it.

When it is showing the rows, it also offers a tick box per column under Columns to show, so you can look at three columns of a wide table without wiring anything up. This changes the view and never the answer: no rows are lost, Copy and Save write exactly the columns shown, and the block in the panel redraws the moment you tick a box, with no re-run. A Select upstream does the same job to the data itself, and the two work together, with Select narrowing what arrives and this narrowing what you see of it. Select does change the answer, so its boxes are the ones that need a re-run.

An Output can be built on. Wire another node after it and that node is handed exactly what the Output is showing, so you can look at an answer and then narrow it without rebuilding the query in front of it. What it shows is what it passes on: a Count passes its count, and a row view narrowed to three columns passes those three columns. That is the one case where the column boxes do need a re-run: this block redraws straight away, but the branch wired after it is still showing the columns it was handed last time, and the panel says so.

An Output used as a step on the way to an answer is often not an answer worth the room, so Show in results panel turns its block off. It is still run and still feeds whatever is wired after it, and only the block goes. Turning it back on does not need another run.

Variables

A variable is a value you name once and then use in as many nodes as you like. It is the answer to a query that keeps repeating the same number: a student ID that goes into two Filters, a pass grade that three nodes compare against, a band width that four Histograms have to share to be comparable at all.

Without one, changing the question means finding every node that holds the old answer. Miss one and the query still runs, quite happily, asking two different questions at the same time. With one, you change the value in one place and every node that uses it follows.

Variables are not nodes and nothing is wired to them. They live behind the yellow Variables button in the toolbar, above the query that uses them, the way a method's parameters are declared above its body. The number beside that button is how many the query has, so a query you did not write says it is parameterised before you open anything.

Where a variable can be used

Anywhere the tool asks you for one value:

  • A Filter condition's value, whatever kind of column it is about: a number, a grade, a specialisation, a course code, a pattern.
  • Either end of a Filter's in range band, separately. "From floor to 9" is a perfectly good range.
  • A Take's row count.
  • A Histogram's band width.

It cannot stand for a list of values (is one of takes several, and a variable holds one), nor for an operator or a column, which are the shape of the query rather than a number in it, nor for a data file, which a Source reads from disk.

A worked example

The question: of the students who passed every course they took, how do their GPAs spread out? And then: does the answer change if "passed" means a C rather than a C-minus?

  1. Add a variable, name it passGrade and give it the value 1, which is a C-minus on the nine point scale.
  2. Build Source → Filter → Histogram → Output. In the Filter, set the condition to Lowest grade ≥ and press the $ beside the value. It now reads passGrade.
  3. Press Run Query and read the distribution.
  4. Change passGrade to 3 in the menu, press Run Query again, and compare. One edit, in one place, and nothing else about the query moved.

The same shape works for a band width. Point three Histograms at the same width variable and their bands can never drift apart, which is what makes the three answers comparable.

Saved with the query. A saved query carries its variables and the values they were last set to, so opening one re-opens the question it was actually asking. The load message names them, because they are usually the first thing to change before running somebody else's query. Deleting a variable that nodes are using asks first, and hands each of those settings back the value that was typed in it.

Reading results

Pressing Run Query fills the panel on the right, one block per Output node, in the order the Outputs were added. An Output with Show in results panel unticked is still run, and still feeds whatever is wired after it, but writes no block here.

Opening, closing and sizing the panel

The panel is open when you first open the tool. Closing it hands its whole column back to the canvas, which is worth doing while a graph is being laid out. Pressing Run Query opens it again, and so does anything else that has something to report, so there is no state in which an answer is written somewhere you cannot see it. Closed, the panel leaves a strip down the right edge with Show on it.

  • Hide, at the top of the panel, puts it away. Show, on the strip, brings it back at the width it had. W does either.
  • The edge between the canvas and the panel can be dragged to any width between narrow and most of the window, and the canvas gives up the space rather than being covered. Double-click it to return to the starting width.
  • The edge sets the width and nothing else. It will not close the panel however far you push it, and while the panel is closed there is no edge to pull: Show is the way back, so a drag can never lose you the panel by accident.

Whether you keep it open, and whichever width you settle on, is remembered the next time you open the tool. It is a setting of your own rather than part of a query: saved .json files carry the graph only, so opening someone else's query leaves your layout alone.

Check a query rather than trusting it. Hovering a wire shows the rows travelling along it and says how many there are, and each block in this panel carries the row count of what reached its Output. Between them you can follow the data step by step and find the point where a result stopped being what you expected.

Saving a query

Save asks you to name the query, then offers two places to put it. Save as file writes the whole graph to a .json file, meaning every node, its settings and every wire. The .json ending is fixed, so a saved query is always one the tool can open again. Save to library keeps the same query in this browser instead. See The query library below. Pressing Enter writes the file, which is what it has always done.

Save a second time and it offers the name you used before, so revising a query does not scatter near-identical files around.

Load opens one back onto the canvas, replacing whatever is there. Only .json files are accepted.

What a file holds is the question, not the answer. Opening a saved query restores the graph, and pressing Run Query evaluates it against the data as it stands at that moment, so the same query re-run next year gives you next year's answer.

The data is never saved with it. A query file records the names of the files each Source was given and nothing out of them: no student, no grade, not even a course code. That is deliberate. Queries get emailed around, and student records should not travel with them.

So loading a query gives you the graph back with every Source empty, and each Source then names the files it was built against. Choose them again and the query answers exactly as it did before. A query saved last year and loaded against this year's files is the same question asked of new data, which is the whole point of keeping one.

The query library

Save and Load write and read a file. Library keeps the same queries in this browser instead, so a query built once is one click away next term rather than something to go and find in a folder.

It opens as a grid of cards. Each card shows a small picture of the query (the nodes and the wires between them), because the shape is what you built and what you will recognise. Type in the search box to narrow the grid by name.

OpenPuts that query on the canvas. If there is already something there it asks once, on the button, because there is no undo.
RenameEdits the name in place. Enter keeps it, Esc abandons it.
ExportWrites that one query out as a .json file, the same file Save writes and Load reads. This is how you send a query to a colleague, and how you keep a copy that survives the browser.
DeleteRemoves it. Asks once, on the button, and there is no way back.

The box at the bottom names the query on the canvas and Save to library puts it in. If a query of that name is already there, the button asks whether to replace it rather than quietly adding a second card with the same name. The Save button in the toolbar offers the same choice, so you can reach the library without opening it.

Taking it with you

Export library writes every saved query out as one .json file. That file is the backup, and it is also how you hand a set of queries to a colleague: they press Import and choose it.

Import merges, and never replaces. Anything in the file whose name is already in your library is left alone, and the tool tells you how many it added and how many it skipped. Your own queries cannot be overwritten by somebody else’s file. If you do want their version of a query you already have, rename yours first and import again.

Import also accepts a single saved query (the kind Save as file writes) and files it under the file’s own name. The two look the same in a folder, so there is nothing to get wrong.

A card holds the question, not the answer, exactly like a saved file. No student, no grade and no course code is ever kept in the library. Opening a card gives you the graph back with every Source empty, and each Source then names the files it was built against.

What the library is not

It is not a backup. It lives in this browser on this machine. Clearing site data removes it, a private window never sees it, and it does not follow you to another computer or another browser. Anything you would be sorry to lose should be exported to a file as well: one card at a time with Export, or the lot with Export library.

It is not private on a shared computer. The library belongs to the browser profile, not to the person sitting at it, so whoever uses this machine next sees the same cards. That is safe as far as the data goes, because no records are in there, but a query’s own settings can name a specific student if you typed one into a Filter, and that would sit on a card until somebody deletes it.

There is a limit on how much a browser will store, and on how many queries the library will hold. If either is reached the tool says so and refuses the save rather than dropping it quietly; export a few and delete them to make room.

Query library

The Query Library is a way to save and store necessary queries built onto this application itself. From here you can save, rename, export, edit, open, and delete any queries that you have made. You can also import query .json files from your device into this library, or export the entire library as one .json file containing every query.
